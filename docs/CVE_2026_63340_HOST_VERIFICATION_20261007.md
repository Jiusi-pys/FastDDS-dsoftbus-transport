# CVE-2026-63340 Host verification on the ROS 2 maintenance candidate (2026-10-07)

Task: `CANDIDATE_SECURITY_MITIGATION_FROM_3BE5492`, baseline
`3be549253a8edfb88793291f040a0f24a2bd05e6` on `claude/dsoftbus-transport-20260924`.

This document records an **isolated Host** verification of the configuration-led
mitigation for CVE-2026-63340 on the Fast DDS `2.14.7` / Fast CDR `2.2.8`
maintenance candidate, plus the malformed CDR sequence-length tests that the
previous candidate package recorded as not executed. It is execution evidence
for a bounded set of Host scenarios. It is **not** a device result, not a
production qualification, and not a claim that the advisory has an upstream fix.

## 2. Exposure surface actually traced

| Boundary | Where | Consequence |
| --- | --- | --- |
| Host opaque-byte seam | `integrations/ros2/HostSocket.cpp` caps a record at 65536 bytes and forwards it unchanged | A small transport record can still advertise a large RTPS `sampleSize` |
| Adapter input lease | `src/InputChannels.cpp` `InputReceiverLease::InvokeValidated` calls the retained `TransportReceiverInterface::OnDataReceived` | Route/lease checks precede the parser but do not interpret `sampleSize` |
| Upstream receive entry | candidate `src/cpp/rtps/network/ReceiverResource.cpp` calls `MessageReceiver::processCDRMsg` | The record buffer is borrowed for the synchronous call |
| Security dispatch | candidate `src/cpp/rtps/messages/MessageReceiver.cpp` decodes real message/submessage crypto and dispatches `DATA_FRAG` | Protection cannot be represented by a test flag |
| Wire `sampleSize` | candidate `MessageReceiver.cpp` reads `uint32 sampleSize` and forwards it to reader handling | No deployment maximum occurs in this parser path |
| Reader reservation | candidate `src/cpp/rtps/reader/RTPSReader.cpp` derives `reserve_size` from the incoming sample size unless `fixed_payload_size_ > 0`, then calls `IPayloadPool::get_payload` | Arithmetic validation does **not** bound a large but representable request |

Note on class names: in this candidate `StatefulReader` derives from
`RTPSReader`, and the reservation sink on this path is `RTPSReader.cpp`. The
advisory names `BaseReader`, which is not compiled into this candidate. The
reported behaviour was reproduced at the class this candidate actually runs.

What was **not** assumed: that DSoftBus authorization equals DDS endpoint
authentication; that `SECURITY=ON` means the plugins ran; that a small RTPS
frame implies a small `sampleSize`; that business QoS `max_samples` bounds
discovery memory; or that a successful authentication makes every later input
from that peer safe.

## 3. The security profile that was actually enabled

One profile only. The candidate default remains `SECURITY=OFF`; nothing here is
a production default switch.

| Item | Value |
| --- | --- |
| Dependency build | Fast DDS 2.14.7 rebuilt with `SECURITY=ON`, OpenSSL 3.3.2, MSVC 19.44 Release `/MD`, isolated prefix |
| Compiled support | installed `fastrtps/config.h` reports `HAVE_SECURITY 1` |
| `discovery_protection_kind` | `SIGN` |
| `liveliness_protection_kind` / `rtps_protection_kind` | `NONE` |
| `metadata_protection_kind` / `data_protection_kind` | `NONE` (topic rule) |
| `allow_unauthenticated_participants` | `false` |
| `enable_join_access_control` | `true` |

Because topic-level `data_protection_kind` is `NONE`, user data from an
**already authorized and matched** peer is not submessage-protected. That is
deliberate and is the residual-risk boundary described in section 6; it is not
covered by the unauthenticated-scenario result.

Identity material is generated by
`tests/ros2_host/security_candidate/generate_isolated_pki.py` into the
repository build isolation, with a literal `NONPRODUCTION / CVE63340-Isolated-Test`
subject marker. No real user, device, vendor or product key is used, no
generated private key is committed, and the generator refuses to write into the
source tree. Normal certificate lifecycle and production issuance are **not**
claimed to be complete.

## 4. Where each input was stopped

Every scenario starts the subscriber role and the publisher role as two
independent OS processes on loopback only. The driver is
`tests/ros2_host/security_candidate/run_security_matrix.py`; the receipt is
`build/candidate-security-mitigation-20261007/runs/SECURITY_MATRIX_RESULT.json`.

| # | Scenario | Observed | Layer that decided |
| --- | --- | --- | --- |
| 00 | Baseline: two ordinary participants, no security at all | matched and delivered | control for the harness itself |
| 01 | Authenticated authorized pair, discovery `SIGN` | matched and delivered, plugins report `AUTHORIZED` | authentication + access control + crypto all passed |
| 02 | Plain peer against the secure subscriber, discovery `SIGN` | no match either side; secure side reports repeated `UNAUTHORIZED` and **never reports the peer as discovered** (0, stable over repeats) | plugin authentication gate; the peer never becomes a discovered endpoint |
| 03 | Plain subscriber against the secure publisher, discovery `SIGN` | no match either side; secure side reports `UNAUTHORIZED` and 0 discovered participants | same gate, opposite direction |
| 04 | Valid certificate chain, grant does not cover the governed domain or topic | reader creation refused: `topic not found in allow rule` / `Error checking creation of local reader` | **access control**, not authentication, and at local endpoint creation |
| 05 | Control with four governance fields moved to the unmitigated setting (discovery `NONE`, unauthenticated accepted, join access control off) | still no match, `Security manager returns an error for reader`; the secure side reports the same plain peer as discovered (1) | see the attribution note below |
| 06 | Control: secured pair with discovery protection `NONE` | matched and delivered | the harness observes a successful authenticated pairing |
| 07 | Authorized pair, 200000-byte samples | 3 samples / 600000 bytes delivered, contiguous | the sample far exceeds the 65500-byte UDP datagram limit, so the transport must fragment it; exact reassembly and delivery were observed (no per-fragment counter was observed) |
| 08 | Security plugin declared, governance document absent | participant creation failed | fail closed, no silent fall-back to non-secure |
| 09 | Same, identity certificate absent | participant creation failed | fail closed |
| 10 | Single-knob probe: **only** `allow_unauthenticated_participants` flipped to true; discovery protection stays `SIGN` and join access control stays on | still no match; the secure side reports the plain peer as discovered (1), exactly as in scenario 05 | see the attribution note below |

### What the discovery numbers attribute, and what they do not

Three configurations were run against the same pairing — secure subscriber versus a
peer with no security configuration at all — and the count of discovered
participants on the secured side was 0, 1 and 1 respectively. The matrix asserts
each of those counts, so a regression in any row fails its scenario:

| Governance | `discovery_protection_kind` | `allow_unauthenticated_participants` | join access control | discovered | scenario |
| --- | --- | --- | --- | --- | --- |
| candidate profile | `SIGN` | `false` | on | **0** | 02, 03 |
| single-knob probe | `SIGN` | `true` | on | **1** | 10 |
| unmitigated control | `NONE` | `true` | off | **1** | 05 |

**Two conclusions, both negative for attribution.**

*Which field stops the unauthenticated peer from matching?* **Not isolated, and not
`discovery_protection_kind`.** Scenario 05 moves four governance fields at once and
the plain peer is still refused. Scenario 10 then moves **only**
`allow_unauthenticated_participants`, leaving discovery protection at `SIGN`, and
reproduces the same discovered-participant count as scenario 05. The count the matrix
measures is therefore governed by `allow_unauthenticated_participants`, and this
matrix never isolates `discovery_protection_kind` from it. What the three rows do show
is that under the candidate profile the unauthenticated peer is never admitted as a
discovered participant, while the two documents that admit unauthenticated
participants do admit it.

*What stops it with DDS Security enabled at all?* Enabling a PKI-DH authentication
plugin plus join access control is sufficient to produce the endpoint refusal here,
so the refusal alone cannot be credited to any single governance field.

For the reported unauthenticated discovery-to-fragment scenario, the peer is shown
never to become a matched writer under the candidate profile, so no reader
reservation triggered by that peer occurs. It is **not** shown that
`discovery_protection_kind` is the setting responsible for that, and it is not shown
that every possible unauthenticated byte sequence is discarded earlier than the
parser.

## 5. Where the allocation decision is taken

`tests/ros2_host/security_candidate/secure_probe/bounded_payload_pool_tests.cpp`
installs a test-owned `IPayloadPool` on a real RTPS reader and calls the public
`RTPSReader::reserveCache`. Receipt:
`build/candidate-security-mitigation-20261007/runs/BOUNDED_PAYLOAD_POOL_RESULT.json`.

| Observation | Result |
| --- | --- |
| Ordinary 4096-byte reservation, resizable history | pool asked for exactly 4096; granted |
| `sampleSize = 0x7FFFFFFF`, resizable history | **the reader asked the pool for all 2147483647 bytes**; only the test ceiling refused it |
| Fixed `PREALLOCATED` history, payload maximum 4096, `sampleSize = 0x7FFFFFFF` | the reservation is **clamped to 4096**; the pool is never asked for the wire size |
| Fixed history, `sampleSize` one byte above the maximum | still clamped to 4096 |

Two conclusions, kept separate:

* This is where the decision is taken, and for a resizable reader the reported
  oversized request is reachable. A deployment that configures a bounded
  fixed payload maximum bounds this request as a side effect. **This task does
  not choose such a limit for production**, and the test ceiling is a test
  safety control and an observation device, never a product limit and never
  evidence that the library refuses anything.
* This is a direct call into a public library method. It shows local behaviour
  only. The security matrix carries the separate evidence about the real entry.

**What this test does not exercise.** The public
`RTPSReader::reserveCache(CacheChange_t**, uint32_t)` overload passes
`fragment_size = 0`, so the fragment-geometry branch of
`CacheChange_t::calculate_required_fragmented_payload_size` short-circuits and its
"fragment size below the minimum" rejection is never reached here. The real
fragmented call site is `StatefulReader::processDataFragMsg`, which passes the
writer's fragment size. The conclusion above still transfers, because both
branches use `reserve_size = cdr_payload_size` whenever `fixed_payload_size_` is
zero, but the fragment arithmetic itself was not exercised by this test and the
fragmented path is covered only by the end-to-end scenario 07.

## 6. Residual risk that is explicitly not covered

* **Authorized, matched peers are a separate case.** With topic
  `data_protection_kind = NONE`, a matched peer can still send a large but
  legitimate `sampleSize`, and section 5 shows the reader will ask the payload
  pool for it. Discovery `SIGN` does not bound that. It is not covered by the
  unauthenticated-scenario result and is not mitigated by this task.
* Mixed native UDP/TCP transports, relays and unrelated participants were not
  exercised.
* Device behaviour, memory limits and OOM behaviour were not observed. No
  process was deliberately driven to exhaustion; the bounded ceiling exists so
  that it was not.
* Authentication success is not treated as proof that every later input from
  that peer is safe.

## 7. Malformed CDR sequence lengths

The previous candidate package recorded that only normal Fast CDR cases had been
run and that malformed sequence lengths were not tested. This task closes that
for the type the ROS acceptance runs actually carry, `std_msgs`, in two
explicitly separated layers. Receipt:
`build/candidate-security-mitigation-20261007/runs/MALFORMED_CDR_RESULT.json`
(19/19).

**Layer 1 — the real generated rosidl typesupport.** Cases call
`std_msgs::msg::typesupport_fastrtps_cpp::cdr_deserialize` from the
candidate-rebuilt `std_msgs__rosidl_typesupport_fastrtps_cpp` library for
`std_msgs/msg/UInt8MultiArray`, whose `data` member is `sequence<uint8>` and
whose `layout` member contains `sequence<MultiArrayDimension>`. Every malformed
buffer is handed straight to the library; nothing is pre-validated.

Covered: legal empty, ordinary and exact-boundary sequences; declared length one
greater than the bytes present; declared length far beyond the buffer; declared
length `0xFFFFFFFF`; truncated length field; truncated payload; truncated nested
length; a nested sequence that declares an element with none present; and a
valid sample after malformed input. Every malformed input is refused with
`NotEnoughMemoryException`.

**Allocation is not observable at this layer.** The generated library's internal
`resize` calls happen inside its own module, so the harness's allocator override
sees only the allocations it makes itself while formatting the exception. Each
layer-1 case therefore reports `allocation_observability: "not_observable"`, and
no layer-1 claim is made about the size of any request. The bound on layer 1 is
the observed rejection plus the absence of any sanitizer-independent evidence to
the contrary; layer 2 is where allocation is actually measured.

**Layer 2 — Fast CDR's own reader with the allocator observed.** Fast CDR's
sequence reader is a template, so its `resize` is compiled into whichever
translation unit instantiates it. Compiling it here makes the allocation
observable, and these cases report
`allocation_observability: "observed_in_this_translation_unit"`.

Layer 2 finds a real precision point in this Fast CDR version: the guard before
the resize compares the **remaining byte count** against the **element count**,
not against `count * sizeof(element)`. With exactly as many bytes as the
declared count, the guard passes and a resize of `count * sizeof(element)` is
requested before the read runs out and throws.

| Case | Declared | Bytes present | Requests recorded | Reading |
| --- | --- | --- | --- | --- |
| `cdr_05` | 8 × `uint32` | 8 | 32, then 64, 112 | a 32-byte resize admitted before rejection |
| `cdr_06` | 12 × `uint64` | 12 | 96, then 64, 112 | a 96-byte resize admitted before rejection |

The `64` and `112` entries are the allocations made while constructing the
exception, not sequence storage. The amplification is `sizeof(element)` and is
therefore bounded by the incoming size; with the 65536-byte Host record cap it
is not a denial-of-service by itself. It is recorded as an upstream behaviour
observation with a reproducible case, not patched here and not claimed fixed.
After a refused read, a fresh stream still deserialises exactly, and a valid
sample after malformed input is delivered unchanged.

## 8. Dependency instrumentation and loading identity

| Item | State |
| --- | --- |
| Fast DDS 2.14.7 | Rebuilt in isolation with `SECURITY=ON` for the security probes; the candidate default build remains `SECURITY=OFF` |
| Fast CDR 2.2.8 | Candidate build reused; the sequence templates under test are instantiated in the test translation unit |
| Generated typesupport | Candidate-rebuilt `std_msgs` / `rosidl_typesupport_fastrtps_cpp` reused, bound to the `SECURITY=OFF` prefix they were built against |
| Loading identity | The probe directory is placed first in the child `PATH` and the resolved `fastrtps-2.14.dll` / `fastcdr-2.2.dll` paths and SHA-256 digests are recorded in the matrix receipt |
| ASan | Not used. The probes were not built with a sanitizer, so no memory-safety claim is made from them |
| TSan | Not run; unchanged from the previous package's statement |

`HAVE_SECURITY` changes public header layout, so the `SECURITY=ON` library and
the `SECURITY=OFF`-compiled ROS stack must never be loaded in one process. The
security probes are a separate process tree from the ROS runtime for exactly
this reason.

## 9. Normal ROS behaviour under the security configuration

**BLOCKED.** The ROS 2 Host runtime and its `rmw_fastrtps` / `rosidl` /
bridge stack are bound to the `SECURITY=OFF` candidate. Because
`HAVE_SECURITY` changes public header layout, a security-enabled ROS run
requires that whole stack rebuilt against the `SECURITY=ON` prefix. That
rebuild was not performed in this task, so no ROS graph, service, QoS 20/20,
DDS deletion or Runtime-Close result is reported under the security profile.

Nothing in this task modifies any ROS runtime source, so the existing ROS
acceptance evidence for the unchanged candidate artifacts is not invalidated by
it. Reusing that evidence is not the same as running ROS under security, and it
is not reported as such. A security-enabled ROS pass is the next necessary
verification step.

## 10. Installed preflight extension

`scripts/install_preflight.py` gained a read-only `security` configuration
block. It verifies dependency security support, configuration and file
completeness, and refuses unsupported combinations. It does **not** establish
that a certificate is used on a target, that a handshake succeeded, that
malicious traffic is blocked, or that PF/P4 are closed, and it records that
limitation in its own output as `SECURITY_RUNTIME_UNPROVEN`.

| Situation | Result |
| --- | --- |
| `security` absent | every existing pass/fail decision unchanged; the result additionally reports `security_mode = NONE` |
| `DISCOVERY_SIGN` / `DISCOVERY_ENCRYPT`, all six material keys present, inspected tree reports `HAVE_SECURITY 1` | input checks pass; `security_mode` recorded; `production_ready` still false |
| declared mode, inspected tree reports `HAVE_SECURITY 0` | `SECURITY_NOT_COMPILED_INTO_DEPENDENCY`, refused |
| declared mode, no `--fastdds-include`, or the tree has no `fastrtps/config.h` | `SECURITY_DEPENDENCY_NOT_INSPECTED`, refused |
| `fastrtps/config.h` present but `HAVE_SECURITY` undefined | `SECURITY_SUPPORT_UNKNOWN`, refused |
| a required material key absent from the object | `SECURITY_MATERIAL_MISSING`, refused |
| a required material file absent from disk | `SECURITY_FILE_MISSING`, refused |
| relative material path | `SECURITY_PATH_NOT_ABSOLUTE`, refused |
| material present with `mode = NONE` | `SECURITY_MODE_NONE_WITH_MATERIAL`, refused |
| unknown mode or extra field | `SECURITY_MODE_UNSUPPORTED` / `UNKNOWN_SECURITY_FIELD`, refused |

The six required keys are `identity_ca`, `identity_certificate`, `private_key`,
`permissions_ca`, `governance` and `permissions` — `permissions_ca` is required
because the Access-Permissions plugin reads it, and the verified probe sets it.
`--fastdds-include` is caller-supplied and is **not** bound to the manifest's
dependency digest: pointing it at an unrelated include tree that happens to
report `HAVE_SECURITY 1` would still pass, so the caller must point it at the
same dependency build the manifest binds.

The unit suite is 44 cases (31 pre-existing plus 13 security-profile cases).
